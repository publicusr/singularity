# Can Singularity run on macOS? (researched 2026-10-17)

Owner (Round 2, Q2): "would love to have it available on macOS too, fuck Windows for sure."

## The blocker: the Engine

Spotify Soloist (our Linux Engine, ADR-0001) is **Linux-only** (x86_64, aarch64, armv7). Everything
else ports: Rust + ratatui, kitty and Ghostty both run on macOS with the kitty graphics protocol, and
the Catalogue (private API) is platform-independent.

## Engine options on macOS

| Option | Lossless | How we control it | Verdict |
|--------|----------|-------------------|---------|
| **A. The official Spotify desktop app as the Engine** | **Yes**: the desktop app has lossless since 1.2.67 ([Spotify support](https://support.spotify.com/ba-bs/article/lossless-audio-quality/)) | As a **Spotify Connect device** through connect-state, the same code path as D12 (controlling your phone). Locally, the app also has an AppleScript dictionary (`play track … in context …`, position, volume) and posts `com.spotify.client.PlaybackStateChanged` distributed notifications for push events | **Recommended.** Lossless, official audio path, and reuses the remote-control code |
| B. librespot embedded | No (320 kbps Vorbis) | In-process | Fallback if the desktop app isn't installed |
| C. Soloist in a Linux VM/container, audio forwarded over the network | Probably | WebSocket into the VM | Rejected: fragile, and audio has to leave the VM |

Known quirks of A (to verify in the macOS spike):
- The AppleScript `play track` command reportedly **brings Spotify to the foreground** (since
  1.2.31; [community report](https://community.spotify.com/t5/Desktop-Mac/Bug-report-AppleScript-amp-quot-play-track-amp-quot-command/m-p/6938676/highlight/true)).
  This is a reason to drive playback over Connect instead and keep the app hidden (`open -gj`).
- The AppleScript interface has no queue, library or likes. That's fine: those come from the Catalogue.
- The desktop app must be installed and logged in. Singularity would start it hidden and treat it as
  an implementation detail.

## Audio tap for visuals on macOS

PipeWire monitor capture becomes a **Core Audio process tap** (`AudioHardwareCreateProcessTap`, macOS
14.2+/14.4+) on the Spotify app's process. Reference: [AudioCap](https://github.com/insidegui/AudioCap).
Pitfalls: TCC permission (`NSAudioCaptureUsageDescription`); without it the buffers are silently all zero
([write-up](https://dev.to/nickdelv/2000-buffers-of-nothing-3i8)). One Apple forum report mentions zero
buffers on a macOS 26.5 beta ([thread](https://developer.apple.com/forums/thread/825780)). There is no
maintained Rust crate for it, so this means FFI via `coreaudio-sys` following the Swift samples.
Open question for the spike: which binary the permission attaches to when Singularity runs inside kitty.

## Other platform seams

| Concern | Linux | macOS |
|---------|-------|-------|
| Engine | Soloist | Spotify.app over Connect (+ AppleScript) |
| Audio tap | PipeWire monitor of the Soloist node | Core Audio process tap on Spotify.app |
| Daemon autostart | systemd user unit | launchd LaunchAgent |
| Media keys / OS now-playing | MPRIS (D-Bus) | Spotify.app already integrates with Now Playing |
| Secrets | Secret Service (KWallet) | Keychain |
| Config paths | `~/.config/singularity` (XDG) | `~/.config/singularity` (dotfile-friendly) or `~/Library/Application Support` |

**Consequence:** the Engine and audio tap become platform interfaces from day one. Linux ships first
and macOS follows with option A. Windows is out of scope.

## First build on macOS (2026-10-19)

M2 Air, macOS 15.7 (so process taps are available), Spotify.app 1.2.94 installed and logged in, Rust 1.99 via
Homebrew's rustup. The workspace compiled after one change (`prctl` is Linux-only). The Client ran in a pty against a
fake Daemon: every Pane drew, and the GPU Visuals ran on Metal ("Apple M2"). tokio's `peer_cred` gives the peer's pid on
macOS (`LOCAL_PEEREPID`), so the stale-Daemon check only needs `proc_pidpath` instead of `/proc`. The default socket,
`$TMPDIR/singularity-<uid>/singularity/daemon.sock`, is 88 bytes here, under macOS's 104-byte limit. The plan and its
status: `docs/PLATFORMS.md`, tickets #63–#69.

## Update (2026-10-19, evening): the cost of option A, and option B built

Measured on the M2 Air: Spotify.app uses ~600 MB and 5–25 % CPU while playing (hidden); the owner found that too
much, so option B is now an Engine choice on both OSes (D52, #70): librespot inside the Daemon, which idles at ~26 MB.
Lossless stays with option A: librespot gets Ogg Vorbis 320 kbps only (Spotify keeps lossless to its own players;
[forum report](https://community.spotify.com/t5/Desktop-Linux/Lossless-playback-on-third-party-Connect-devices/m-p/7202841/highlight/true)),
and the spotatui fork's player picks Vorbis files only. Option C (Soloist in a VM) is back on the table as the one
lossless route without the app (D53, open).

## Where it ended up (2026-10-20)

Built: all three options. A (the app over Connect) is `kind = "spotify-app"`; B (librespot in the Daemon) is the macOS
default (D54, D56); C (Soloist in a VM) is `kind = "soloist"` on macOS (D55, `2026-10-soloist-vm-spike.md`), with the
VM's networking through gvproxy rather than Apple's NAT (which the owner's VPN drops) and its audio over vsock. The
process tap works mechanically (48 kHz, real time) but, as feared above, hands over silence unless the terminal is
allowed under "System Audio Recording Only" by hand. User-facing summary: the README's "macOS quirks".
