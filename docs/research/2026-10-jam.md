# Jam (social sessions): what a client can do (researched 2026-10-25)

Question (D64): the owner wants Jam management near the Devices panel. Today a second phone does not see the
Jam until the owner opens Spotify on their own phone, which then offers it. This note answers what Singularity
could do itself, so the design can be decided with facts.

**Method.** No login, no account, no keyring, no Daemon, no Soloist, and no requests to Spotify's APIs. I read
Spotify's public web-player JavaScript (downloaded anonymously to `.scratch/jam/sources/`: `web-player.f954508a.js`,
`vendor~web-player.19d7605d.js`, the `dwp-panel-section` chunk), public support pages, the new open librespot
PR that documents Jam, and four open-source Jam implementations. Facts are marked **verified in source** or
**assumed**; "verified" means a request/field is present in running code or in a shipped client bundle, not
that I made the call myself.

## TL;DR

| Question | Answer |
|---|---|
| Can a non-phone device host a Jam? | Yes, if it is a real Connect player and the account has Premium. A librespot bot starts one with `GET /social-connect/v2/sessions/current_or_new?local_device_id=<device>` and hands out `https://open.spotify.com/socialsession/<token>` (**verified** in spoticord; **verified** in librespot's Jam docs). |
| Can Singularity start one? | The calls fit the Catalogue's librespot session (it already has the desktop client id, the dealer and a hidden Connect controller). The open question is whether that session may name **another** device (Soloist's) as `local_device_id`; every implementation I found starts the Jam on its own session's device. Needs one live check. |
| Does a Jam show up in Connect state? | Partly: `PlayerState.session_id` becomes the Jam's session id on the host device, and the dealer's `social-connect/v2/session_update` carries the session, members, permissions and `host_active_device_id`. There is no Jam flag or reason in the cluster proto. Participants and permissions must be read from `social-connect`, not inferred from the cluster. |
| How do nearby phones find it? | Same Wi-Fi: the app resolves local-network tokens/Jam tokens (`resolveJam`); Bluetooth: the host app broadcasts a "social radar" token within ~1 m. A link or a QR code always works. A headless host can print the link and render a QR itself, but cannot emit Spotify's BLE advertisement. |
| Premium? | Premium is needed to **host** and to **join remotely**. A free account can join an in-person Jam and add songs (**verified** in Spotify Support). |
| Recommendation | Build a small "Start a Jam / invite link + QR / End Jam / N guests" block in the Devices panel, only for Engines whose Connect device can really be the host; keep "start from the phone" for Soloist until the cross-device check passes. Don't build "join a Jam" — a guest lands on the host's device anyway. |

## 1. The API

### 1.1 Host, auth, headers

- Host: `spclient`. The web client calls it through `@webgate/social-connect`; the direct form is
  `https://spclient.wg.spotify.com/social-connect/...` or the regional `{region}-spclient.spotify.com` from
  `apresolve` (the same host as `connect-state` and `track-playback`). **verified**: the web bundle builds
  `@webgate/social-connect/v2/sessions/info/{token}` (`web-player.f954508a.js` @2942085); a 2024 Spicetify
  extension calls `https://spclient.wg.spotify.com/social-connect/...` directly; myspoti's capture notes list
  `social-connect` under the regional spclient (`docs/api/SESSION.md:94`).
- Auth: the account's normal spclient auth (`Authorization: Bearer`, and `client-token` where librespot sends
  it). The endpoint refuses an ordinary third-party app token with `403 RBAC: access denied`; it accepts the
  desktop-identity credential (**verified**: Deskthing's Jam notes, 2026). Singularity's Catalogue logs in with
  the Spotify desktop client id `65b708073fc0480ea92a077233ca87bd` (`crates/daemon/src/catalogue.rs:22`),
  the same identity librespot uses, and spoticord's librespot session calls Jam successfully — so our Catalogue
  token is expected to be accepted (**assumed** until the live check).
- The librespot PR says every request should carry `spotify-connection-id` with the dealer connection id, and a
  bodyless `POST` needs `Content-Length: 0` (**verified in source**: PR docs). Spoticord's librespot call sends
  neither an explicit connection id nor a body and works (**verified in source**: `spoticord_player/src/lib.rs`
  `create_jam`), so treat the header as recommended but not proven mandatory.

### 1.2 Requests

All paths relative to the spclient base. `local_device_id` is a Connect device id (librespot's
`session.device_id()` in spoticord, the desktop app's `connectStateId` in the Spicetify extension).

| Action | Method and path | Notes | Status |
|---|---|---|---|
| Read the account's current Jam | `GET /social-connect/v2/sessions/current` | `404` when none; a Jam that was ended can leave a DORMANT record with `active` unset — check `active === true` | **verified** (bundle `vendor~web-player.19d7605d.js` @400362; librespot PR; Deskthing) |
| Start, or get the running Jam | `GET /social-connect/v2/sessions/current_or_new?local_device_id={id}&activate=true&type=REMOTE` | Idempotent: returns the existing Jam instead of starting a second. `activate=true` is what makes it appear on other members' devices. `type` is `REMOTE` for a remote Jam (the enum also has `IN_PERSON`, `REMOTE_V2`) | **verified** (PR; spoticord omits `activate`/`type` and still gets a link; the 2024 extension sends `type=REMOTE`) |
| Read a Jam by its link token | `GET /social-connect/v2/sessions/info/{token}` | Does not join. Returns the session and `session_members` | **verified** (bundle @2942085; 2024 extension) |
| Join | `POST /social-connect/v2/sessions/join/{token}?playback_control=listen_and_control&join_type=deeplinking&local_device_id={id}` | `playback_control` seen as `listen_and_control`; `join_type` seen as `deeplinking`. Other values (`qr`, `nearby`) are likely but unseen | **verified** request form (2024 extension); values **assumed** for QR/BLE |
| Leave (member) | `POST /social-connect/v2/sessions/leave` | The 2024 extension used `POST /social-connect/v3/sessions/{session_id}/leave?local_device_id={id}`; both forms may exist | **verified** path (PR) / variant **verified** in older code |
| End (owner) | `DELETE /social-connect/v3/sessions/{session_id}?local_device_id={id}` | The librespot PR says an owner who only *leaves* hands the Jam on; Spotify Support says a host who leaves ends it for everyone. End explicitly | **verified** path (PR, 2024 extension); a 2026 implementation also used `/v2/sessions/{id}` — confirm which answers |
| Remove a member | `POST /social-connect/v3/sessions/{session_id}/member/{member_id}/kick?local_device_id={id}` | Owner only; `member_id` is `SessionMember.id`, not the username | **verified** (PR); web client exposes `removeSessionMember(sessionId, memberId)` and `kickAllParticipants(sessionId)` |
| Redirect a guest command | `POST /social-connect/v2/sessions/{session_id}/commands/from/{device_id}` | The web client calls this when the session says `redirectCommands`; body is `{command}`. This is how a guest's play/skip reaches the host instead of being sent to the host's Connect device directly | **verified** (bundle `vendor~web-player.19d7605d.js` @401223-401456) |
| Set queue-only mode | not found | Web client has `setQueueOnlyMode(bool)`; the reply is the updated session. No path in the public bundles | **assumed** endpoint; field **verified** |
| Set guest volume control | not found | Web client has `setParticipantVolumeControl(bool)`; field values seen: `ENABLED`, `DISABLED`, `UNAVAILABLE` (default). Spotify Support: shared volume is supported on Chromecast/Amazon Cast, not Bluetooth/AirPlay | **assumed** endpoint; field **verified** |
| Resolve nearby tokens | not found (`resolveJam(tokens[])` in the client) | Takes `{token, discoveryMethod}` pairs and returns `availableJam` + `playbackDeviceInfo`; `discoveryMethod` = `MDNS`, `CONNECT`, `SOCIAL_RADAR_NEARBY`, `LINK`, `LISTENING_ACTIVITY` | client method **verified** (bundle chunk `dwp-panel-section.d73a3ce7.js` @140781, enum @120488); server path **assumed** |

### 1.3 The session object

JSON, from the web client's parser (**verified**: `web-player.f954508a.js` @2932739), with the librespot
protobuf as the older subset. Keys come in `snake_case` or `camelCase`; empty lists may be omitted. Example
(shape, not a captured answer):

```json
{
  "timestamp": "175...",
  "session_id": "....",
  "join_session_token": "AbC123...",
  "join_session_url": "hm://.../sessions/join/AbC123...",
  "join_session_uri": "spotify:socialsession:AbC123...",
  "session_owner_id": "<user id>",
  "is_session_owner": false,
  "active": true,
  "session_members": [
    {"id": "<user id>", "username": "...", "display_name": "...", "image_url": "...",
     "large_image_url": "...", "is_listening": true, "is_controlling": true}
  ],
  "queue_only_mode": false,
  "participantVolumeControl": "DISABLED",
  "wifi_broadcast": false,
  "is_paused": false,
  "is_jam_paused": false,
  "hostActiveDeviceId": "<connect device id>",
  "host_device_info": {"device_name": "...", "device_type": "..."},
  "user_capabilities": {
    "invite": true, "remove_participants": false,
    "manage_participant_settings": false, "ask_to_upgrade": false
  }
}
```

- `join_session_url` is only returned to the owner and is an internal address only Spotify's apps open; do not
  show it. The shareable link is built from the token (below). **verified** (PR).
- Our vendored `social_connect_v2.proto` (librespot-protocol 0.8.6) has `session_id`, `join_session_token`,
  `join_session_url`, `session_owner_id`, members, `join_session_uri`, `is_session_owner`, `is_listening`,
  `is_controlling`, `is_discoverable`, `initial_session_type`, `host_active_device_id`. It **lacks**
  `active`, `queue_only_mode`, `participantVolumeControl`, `wifi_broadcast`, `is_paused`/`is_jam_paused`,
  `host_device_info` and `user_capabilities`. **verified** from the proto file. A typed parse drops those
  fields; read the answer as loose JSON (or update the proto) — the PR makes the same point about
  `SessionUpdate` reasons.
- `SessionMember.id` vs `username`: compare the owner against both; the PR notes some clients send one or the
  other. **verified** (PR).
- `join_session_uri` is shown above as `spotify:socialsession:{token}` by analogy with the legacy code; spoticord
  only takes the token from the last path segment of `join_session_url`/`join_session_uri` and never uses the URI
  form. The exact URI scheme is **assumed**.

### 1.3.1 Guest permissions

- **`queue_only_mode`** (bool). `false`: a guest may add to the queue **and** control playback (play/pause/skip).
  `true`: add only. Spotify Support's "Let others change what's playing" toggle is this field. The field is
  **verified**; the exact enforcement per command is **assumed** from Support (and check #4).
- **`participantVolumeControl`**: `ENABLED`, `DISABLED`, or `UNAVAILABLE` (default). The host's "Let guests change
  volume". Support says shared volume works on Chromecast/Amazon Cast, not Bluetooth/AirPlay, so a Soloist or
  librespot host may report `UNAVAILABLE`. **verified** field; capability per device **assumed**.
- **Join's `playback_control`**: `listen_and_control` (seen) asks for control. A listen-only join is probably
  `listen`; **assumed**, not seen.
- **`user_capabilities`** tells the current account what it may do: `invite` (share the link), `remove_participants`
  (kick), `manage_participant_settings` (the two toggles), `ask_to_upgrade` (show a Premium upsell). **verified**
  (web parser).
- **`session_members[].is_listening` / `is_controlling`** show who listens and who currently controls; use them in
  a participant list rather than assuming. **verified** (proto + web parser).

### 1.4 Links, QR and the Spotify Code

- Canonical invite link: `https://open.spotify.com/socialsession/{token}`. The token is letters and digits only.
  **verified** in four independent implementations (2024 extension, spoticord, Deskthing, web bundle's
  `shortLink` flow).
- Short link: Spotify's apps share a `https://spotify.link/...` link that redirects to the long one; sometimes it
  answers with a page naming the session. Fetch only `spotify.link` and read the start of the page; keep only
  `[A-Za-z0-9]` in a request path. **verified** (PR).
- QR: the web client asks `@webgate/url-dispenser/v1/generate-url` for a short URL with
  `app_destination=socialsession`, `ssp=1`, `utm_medium=qr` (or `share-link`) and a preview image
  `https://shareables.scdn.co/publish/socialsession/{token}`. **verified** (bundle @2940166-2940399). The QR
  itself is just that URL encoded — a host can generate it locally (no Spotify call).
- Legacy "Spotify Code": `https://scannables.scdn.co/uri/plain/png/{bg}/{fg}/{width}/spotify%3Asocialsession%3A{token}`
  (2024 extension, commented out there as replaced by newer QR codes). **verified** in old source; current
  availability **assumed** not needed.

### 1.5 Dealer updates

- Topic: `social-connect/v2/session_update` (librespot's dealer accepts it without the `hm://` prefix).
  Payload is a `SessionUpdate`: the new `session`, a `reason`, and `updated_session_members`. **verified** in
  librespot-connect 0.8.6 `spirc.rs:232-234` and PR.
- Reasons (union of the proto and the web client's enum): `NEW_SESSION`, `YOU_JOINED`, `USER_JOINED`,
  `USER_LEFT`, `USER_KICKED`, `PARTICIPANT_PROMOTED_TO_HOST`, `DISCOVERABILITY_CHANGED`, `SESSION_DELETED`,
  `YOU_LEFT`, `YOU_WERE_KICKED`, plus reasons **not in the proto**: `WIFI_BROADCAST_CHANGED`,
  `SESSION_MEMBER_PAUSE_CHANGED`, `VOLUME_CONTROL_PERMISSIONS_CHANGED`,
  `QUEUE_ONLY_MODE_CONTROL_CHANGED`, `ACTIVE_DEVICE_CHANGED`, `SESSION_MEMBER_UPDATED`,
  `SESSION_ACTIVATED`. **verified** (bundle @2932739-2933694; librespot spirc's fallback for
  `WIFI_BROADCAST_CHANGED`; PR).
- Read the payload as loose JSON first and switch on `reason` as text. A typed protobuf parse fails on the
  unknown reasons and the update is lost. **verified** (PR; spirc `FallbackWrapper`).
- An update may arrive with no members; it says nothing about who is in the Jam, so keep the last list.
  **verified** (PR). The last reasons in the list end the Jam for this account.
- Guest control commands are not necessarily ordinary Connect commands. The web client sends them through
  `POST /social-connect/v2/sessions/{session_id}/commands/from/{device_id}` when the session answers with
  `redirectCommands` (**verified**: `vendor~web-player.19d7605d.js` @401223-401456). The host device then sees the
  effect as a player-state change, and the librespot PR also saw the owner's playback arrive as `transfer`
  requests (below). D63's "a Jam's commands are ordinary Connect commands" is therefore only part of the story;
  a host Engine must also follow the dealer transfer path.
- The owner's playback also arrives as dealer **`transfer` requests** with
  `from_device_identifier = social-connect-{hex}`, `restore_paused: restore`, `restore_position: extrapolate`,
  `restore_track: always_play_something`, `retain_session: retain_original`, and a base64 `TransferState` whose
  queue may be empty. One also arrives when the account leaves, so not every one means "start playing".
  An ordinary transfer request while a Jam member answers `410 Gone`. **verified** (PR).

### 1.6 Where a Jam shows in Connect state

- **`PlayerState.session_id`** (player.proto field 23): the shared session id. librespot starts with its own
  random UUID (`librespot-core/src/session.rs:143`); when a `SessionUpdate` names this device as
  `host_active_device_id`, spirc replaces its `session_id` with the Jam's and puts it in its next
  `PutStateRequest` (`librespot-connect/src/spirc.rs:2008-2019`, `1054`). So on the host device the cluster's
  `player_state.session_id` is the Jam's `session_id`. **verified in source**.
- **`host_active_device_id`** lives in `SessionUpdate.session`, not in the cluster. There is no Jam field in
  `Cluster`, `ClusterUpdateReason`, or `DeviceInfo`. **verified** from `connect.proto` / `social_connect_v2.proto`.
- **`session_command_id`** (player.proto field 35): a generic field of the web player's player state; I found no
  Jam-specific use. Treat it as unknown, not as a Jam marker. **assumed/unverified**.
- **`PlayOrigin.feature_identifier`**: the web client plays a track picked in the Jam sheet with
  `play(..., {featureIdentifier: "jam", referrerIdentifier: "deeplink"})` (`web-player.f954508a.js` @1733833).
  So a guest's play can carry `"jam"`; it is a hint about one command, not the host's state. **verified in source**.
- **`DeviceInfo.is_social_connect`** and **`is_group`**: present in `connect.proto`; the web device picker maps
  `is_group` to its group-device UI, not to Jam. Neither is a dependable "this device hosts a Jam" flag.
  **assumed**.
- Practical consequence: the UI can read Jam state from `GET /sessions/current` when the Devices panel opens and
  keep it live with `session_update`. The cluster alone can tell you the host's `session_id` but not who is in the
  Jam, whether guests may control playback, or whether the Jam still exists.

## 2. Discovery: how nearby phones learn about a Jam

Spotify's own clients use four paths (**verified** in the web bundle's device picker and Spotify Support):

1. **Same Wi-Fi / local network.** The app asks its native broadcasting API for `getLocalNetSessionDevices()`
   (tokens from mDNS), and also takes every local-network Connect device's `connectStateId`, then calls
   `resolveJam([{token, discoveryMethod: "MDNS" | "CONNECT"}])`. The answer names the Jam and its
   `playbackDeviceInfo` (device id, name, type). **verified**: `dwp-panel-section.d73a3ce7.js` @140345-140781.
2. **Bluetooth proximity ("social radar").** The host session carries
   `device_broadcast_status.social_radar_token.token`; the app calls
   `startBroadcastingBluetoothSessionDevice(token)`, gated by the `enableBLEJamBroadcasting` feature flag.
   Nearby phones with Bluetooth permissions get the invitation (Support: up to ~1 m). The BLE advertisement
   itself is app-native and not in the public bundle. **verified in source** (bundle @2937136, @3784146);
   protocol **assumed proprietary**.
3. **Link / QR / Spotify Code.** `https://open.spotify.com/socialsession/{token}`, its QR, or the legacy
   `spotify:socialsession:{token}` code (section 1.4). Always works, needs no proximity.
4. **Listening activity / Spotify Messages.** `discoveryMethod: LISTENING_ACTIVITY`; Premium only; not relevant
   to a headless host. **verified** (enum and Support).

What a host **device without the Spotify app** can offer:

- A link and a locally generated QR in the TUI. This is enough for the owner's scenario: the second phone scans
  the QR or opens the link, no Spotify app on the host phone needed. **verified** for the link; QR generation is
  ordinary local work (the web app does the same with a URL dispenser only for short links).
- Its normal Connect presence. A Jam hosted on a local-network speaker/device is offered to nearby phones through
  the `CONNECT` discovery path above; Support says Jams work with smart speakers and most Bluetooth speakers.
  Whether the **mobile** app resolves a non-Spotify Connect device the same way the web client does is
  **assumed** — worth one check with Soloist on the LAN.
- It **cannot** emit Spotify's BLE social-radar advertisement or the app's Wi-Fi auto-invite. Those live in the
  official client's native broadcasting stack. A desktop Spotify app (the AppEngine) can, because it is the app.
- The TUI has no camera, so "scan a QR to join" is out; a pasted link is possible if joining is ever built.

## 3. Who can host

- **Premium is required to host** (and to join remotely). Free users can join an in-person Jam and add songs.
  **verified**: Spotify Support, "Start or join a Jam" (2026-10-25); the web client's `getEnabled` returns
  `RESTRICTED` for accounts that may not host (myspoti's capture: free account → `RESTRICTED`).
- The host does **not** have to be a phone. Spotify Support lists desktop, TV, Android Auto and CarPlay, and says
  Jams work with smart speakers and most Bluetooth speakers. The host is the **device that plays**, named by
  `host_active_device_id`; guests' commands reach it either as Connect commands or through the session's
  `commands/from` redirect (§1.5). **verified** (Support; PR; web bundle).
- A **listed Connect device with a session** can start one through the API: spoticord does it from a librespot
  bot on its own device id and returns the link. **verified in source** (spoticord, 2026-10-16). The librespot
  PR states the same for any listed librespot device.
- The device must be a real player. A **hidden controller** (Singularity's `ConnectRemote`, `capabilities.hidden
  = true`, `crates/daemon/src/connect.rs:168-175`) is listed but is not a playback target; making it the host
  would give guests a Jam on a device that cannot play. **assumed** (nothing in the protocol forbids it, but it
  makes no product sense).
- One Jam per account at a time: `current_or_new` returns the running one rather than creating a second.
  **verified** (PR; Deskthing). If the account is already a guest in someone else's Jam, Start must not pretend to
  create a new one; read `is_session_owner`/`session_owner_id` and show "in <owner>'s Jam" instead. **assumed** for
  the guest case, from idempotency.
- Owner semantics: Support says a host who leaves ends the Jam for everyone; the librespot PR says an owner who
  only leaves hands it on. Use `DELETE` to end, and treat "leave as owner" as a live check before relying on
  either. **conflict, unresolved**.

## 4. Fit with Singularity

### 4.1 Which session could make the calls

| Session | Can call `social-connect`? | Can host on its own device? | Notes |
|---|---|---|---|
| **Catalogue's librespot session** (`catalogue.rs`, desktop client id, dealer + hidden controller) | Yes — `session.spclient().request_as_json(...)` is public; the dealer is already running for the cluster | Only on its **hidden controller** device, which cannot play | Best place for reads (current/info), member list and end. For start, it needs to name the Engine's device as `local_device_id` (unverified) or the Jam would point at the hidden device. Also the natural place for `session_update` listeners. |
| **Librespot Engine** (`librespot.rs`, macOS default; available on Linux) | Yes — it owns a real Connect device and a session | Yes — this is exactly spoticord's case | The session lives inside `Receiver` and is not exposed; an `Engine` command or a small handle would be needed. Spirc already keeps `session_id` and listens to `session_update`. |
| **Soloist** (Linux default) | No — it is a separate process with its own credentials/pairing; the Daemon never sees its access token | Only if a request from our session may name Soloist's device (the open question) | Soloist is a normal Connect player and supports being the Jam host today when the phone starts the Jam. Its device id is in the cluster (the UUID it logs as `device_id=`). |
| **Spotify app (AppEngine, macOS)** | The app could, but we don't have its session; AppEngine drives it over Connect only | Yes, from its own UI | The user can start a Jam in the app today; the point of the ticket is not to need the app. |
| **Hidden controller** | Yes | No (no audio) | Use for observing/ending, not for hosting. |

The single fact that decides the design: **does `current_or_new` accept a `local_device_id` that is not the
calling session's own device?** Every implementation found uses its own device; the librespot doc's wording
("the device must already be listed ... its id is sent as `local_device_id`") suggests it may accept any device
on the account. If yes, the Catalogue session can start a Jam on Soloist and the feature works on Linux. If no,
Jam start belongs to the librespot Engine (and the AppEngine on macOS), and Soloist keeps "start from the phone".
This is check #2 below.

### 4.2 Risks

- **Private API / breakage.** Undocumented, mixes v2 and v3, and the paths have already changed between 2024
  and 2026 implementations. Treat it like the rest of the Catalogue: behind a narrow module, degrade to "Jam
  unavailable" and never break playback. The repo's risk note (`2026-10-private-api-risk.md`) applies: breakage
  is the real risk, not bans.
- **RBAC / client identity.** An ordinary app token is refused (`403 RBAC: access denied`). Our Catalogue uses
  the desktop client id, so it should be accepted, but this is the first thing a probe should print.
- **Premium.** The owner has it; a free account must get a clear "hosting a Jam needs Premium" message, not a
  generic failure. Joining in-person as a free guest is allowed and is not our case.
- **Rate limits.** No documented limit. One request per user action, no polling: read `current` when the panel
  opens and rely on `session_update` afterwards; back off on 429/5xx with jitter like the rest of the Catalogue.
  **assumed**.
- **State changes are social.** Starting, ending, kicking and permission toggles affect other people's phones.
  Every one must be an explicit user action with a confirmation where destructive, never a startup side effect.
  Never end a Jam we do not own (`is_session_owner` false); never kick without a confirmation.
- **Secrets.** The join token is a bearer-like invitation: anyone with the link can ask to join. Show it in the
  UI, do not log it, do not put it in fixtures or crash reports.
- **Dormant records.** `GET current` can return an ended session (`active` unset). Use `active === true` as the
  source of truth, or a stale "Jam on" survives forever. **verified** (Deskthing).
- **D63 interplay.** Ordinary Connect play/queue commands are one half; a Jam host also gets `transfer` requests
  from `social-connect-{hex}` and guest commands redirected through `commands/from/{device}` (§1.5). The Daemon's
  D63 rule (follow a change it did not make, never put remembered state back) still applies, but a Jam started
  from Singularity would exercise the transfer path that D63's phone test did not. The librespot Engine's Spirc
  already listens to `session_update` and handles transfers; Soloist is a full client and handles them when the
  phone starts the Jam today. The Catalogue's hidden controller is the right place for account-level reads, not
  for playing. Adding Jam UI must not add a poller that races the player.

## 5. Options for "Jam management"

Each option lists what is verified vs assumed.

### A. Start/end + invite in the Devices panel (recommended first)

A "Jam" section or popup: when there is no Jam, **Start a Jam**; when there is one, **Jam on · N guests**,
**Invite** (link + QR, drawn as Unicode half-blocks or a kitty image), and **End Jam** if we own it.
Reads `current` on open, starts with `current_or_new`, ends with `DELETE`, updates from `session_update`.

- **Verified:** all four requests, the session fields, the link form, the dealer topic, the active/dormant rule,
  QR-as-link.
- **Assumed:** that our Catalogue session may start the Jam on the Engine's device (check #2); that a locally
  drawn QR is acceptable (it is a standard QR of the link); screen space in the Devices panel.
- **Effort:** small. This is the direct answer to the owner's problem: after `activate=true`, the second phone
  sees the Jam without the host phone opening Spotify.

### B. A + participant list, kick, guest permissions

Adds the member list (`display_name`, `is_listening`, `is_controlling`), **Remove** per guest (owner only), a
**Guests can change what plays** toggle (`queue_only_mode`) and a **Guests can change volume** toggle
(`participantVolumeControl`), gated by `user_capabilities`.

- **Verified:** the member fields, `user_capabilities`, the kick path, the permission fields and the web client's
  method names.
- **Assumed:** the permission endpoint paths and HTTP verbs (not in any public source I found); the volume enum
  values; whether a non-Cast host supports shared volume (Support says Chromecast/Amazon Cast only, so on
  Soloist this may be `UNAVAILABLE`); the kick `member_id` on our account's payloads.
- **Effort:** medium. Only worth it if the owner wants moderation from the TUI; the phone already does it.

### C. Join a Jam from Singularity (not recommended)

Paste a link, `GET info`, `POST join`, then the account is a guest. But a guest listens on the host's device, not
on Singularity; an ordinary transfer while a member answers `410 Gone`, and "listen along" is a different
feature. It adds a confusing state ("Singularity is in a Jam but is not playing") for little gain.

- **Verified:** the join request form and the `410` on transfer.
- **Assumed:** what joining from a desktop Connect device does to its local playback.
- **Effort:** small code, high product confusion. Skip.

**Recommendation.** A, behind the live check that a Jam started from Singularity actually lands on the playing
Engine's device. If check #2 fails, implement A only for the librespot Engine (where the calling session owns
the device) and keep the README's "start the Jam from your phone" for Soloist. B only after A is used and the
owner wants moderation; C no.

## 6. Live checks for the owner

These need the owner's account and a phone, and change account state (a Jam starts/ends), so they come after the
design is agreed. The probe is `crates/daemon/examples/jam_probe.rs` (T0034): it uses the same saved Catalogue
login as `connect_probe`, registers a hidden controller for the run and removes it afterwards. It prints structure
only, never access tokens; the one exception is the invite link the owner asked for. `start`, `end`, `kick` and
`perm` ask for `y` on stdin before sending. Run everything from the repo root; `jam_probe -- --help` lists the
commands and each command has its own `--help`.

1. **Read, no Jam.** With Singularity logged in and nothing running:
   `cargo run -p singularityd --example jam_probe -- current`
   Expect `HTTP 404` (or a session with `active: false`). If the output contains a join token, do not paste it
   anywhere; the probe itself does not print one.
2. **The decisive one: start on the playing device.** Play something on Singularity (Soloist on Linux, librespot
   on macOS), then:
   `cargo run -p singularityd --example jam_probe -- devices`
   `cargo run -p singularityd --example jam_probe -- start --device "<that device's name>"`
   The first line is the verdict: `Jam hosted on <name>`, `Jam hosted on the hidden controller`, or
   `start failed: HTTP <code>`. Look for: the answer's `host_active_device_id` is that device's id (not the hidden
   controller's); playback keeps going; the probe's `cluster player_state.session_id` equals the Jam's
   `session_id`; the second phone's Spotify shows the Jam / the QR joins it. **If `host_active_device_id` is the
   hidden controller or the start fails with 4xx, the cross-device form does not work** — that is the answer that
   scopes the feature to the librespot Engine.
3. **Invite and join.** With the Jam from #2 running, open the link printed by `start`, or scan its QR, on the
   second phone. On the phone: join, add a song to the queue, skip a track. On Singularity: the queue and the track
   change within about a second (D63's behaviour), and `jam_probe -- current` shows the guest in
   `session_members` (count goes to 1).
4. **Permissions.** In the phone's Jam settings, turn "Let others change what's playing" off, then on; turn
   "Let guests change volume" on/off. Watch `jam_probe -- current` report `queue_only_mode` and
   `participantVolumeControl` change; a guest's skip should be refused while queue-only is on. The probe can
   change the same settings itself:
   `cargo run -p singularityd --example jam_probe -- perm queue-only on|off`
   `cargo run -p singularityd --example jam_probe -- perm volume on|off`
   These paths are assumed: each candidate is printed with its HTTP status, and the first that answers wins.
   `no candidate answered` means every tried path was 404/405/400-ish.
5. **Kick and end.** As owner, remove the guest from the phone or take the `id=` of a member from
   `jam_probe -- current` and run:
   `cargo run -p singularityd --example jam_probe -- kick <member_id>`
   The guest's app leaves. Then `cargo run -p singularityd --example jam_probe -- end`; the guest sees the Jam
   ended, `current` returns `HTTP 404`/inactive, and the phone no longer offers it. The end tries the v2 then v3
   path and prints which one answered. Also check that ending does not stop the music.
6. **Dealer capture.** Run the probe's watcher and repeat join/leave/pause/skip:
   `cargo run -p singularityd --example jam_probe -- watch`
   It prints each `session_update` reason and session fields, and (when they change) the cluster's
   `player_state.session_id` and a guest command's `PlayOrigin.feature_identifier`. Record the reasons seen
   (especially the ones missing from the proto), the `host_active_device_id`, and one guest command's
   `feature_identifier`. This settles the "where does a Jam show in Connect state" question for our code. Ctrl-C
   stops it.
7. **Repeat with the phone starting the Jam** while Singularity plays (today's workaround), then with the
   librespot Engine on macOS. Use `devices`/`current`/`start`/`watch` and compare `host_active_device_id` and the
   cluster fields. This is also the fallback if #2 fails.

**How to read the output.** `HTTP 200` followed by fields is a good read; `HTTP 404` means there is no current Jam
(or the path does not exist, for an assumed permission path). In `current`, `active: (missing)` or `false` is a
dormant record left by an ended Jam. `host_active_device_id` is the device that actually hosts. `members:` lists
`display_name`, member `id`, `is_listening` and `is_controlling`; use that `id` for `kick`. In `watch`, a blank
line then `--- session_update: REASON` is one update; `cluster:` lines appear only when the cluster's Jam id or
play origin changes. The invite link `https://open.spotify.com/socialsession/<token>` is the only line with a
token in it: treat it as the invitation itself.

What each result means: a Jam visible on the second phone without the host phone opening Spotify proves A's
value; `host_active_device_id` naming the hidden controller means we must restrict start to the librespot Engine;
a 403 means the Catalogue's token is not accepted and the whole feature is out until Spotify changes that.
