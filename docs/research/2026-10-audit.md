## Findings

### Fixed in this batch

1. **security** — `daemon.log` was 0644 (world-readable) and names the account and what plays. The Client now creates
   it 0600 (and tightens an old one), `packaging/launchd/install.sh` makes it 0600 before launchd opens it, and the
   Daemon `fchmod`s its own stderr to 0600 whoever started it. Checked: a 0644 file passed as stderr is 0600 a second
   after the Daemon starts.
2. **security** — the Daemon never checked who connected; it relied only on the socket directory's mode, and didn't
   check the directory was its own. On Linux without `XDG_RUNTIME_DIR` that directory is under the shared `/tmp`, so
   another local user who created it first (or a symlink in its place) could put their own socket where Clients look.
   Now `bind` refuses a directory that is a symlink or not ours (or whose parent isn't ours or root's), the Daemon
   drops connections from other uids (`peer_cred`), and the Client refuses a Daemon running as another user.
   Test: `the_socket_never_goes_through_a_symlinked_directory`.
3. **crash** — `config::set_value` panicked when a section wasn't a plain table: an inline table (`ui = { design =
   "nebula" }`, valid TOML) or a stray `ui = 5`, then any change from the Settings page. Now an inline table becomes a
   table with its values, anything else gives way to one; a real table is left where it is. Test:
   `a_setting_is_set_whatever_shape_its_section_has`.
4. **resources** — the Catalogue's caches grew for as long as the Daemon ran: every list, artist page, search, lyrics
   and track name looked at. Now bounded: expired entries go first, then the oldest (lists 40, artist pages and
   searches 60, names 2000, lyrics 300). Test: `caches_stay_bounded`.
5. **security (hardening)** — cover downloads were read whole and decoded with the image library's default limits
   (512 MB). Now a cover over 8 MB is refused (the Client's covers and the Daemon's notification cover), and decoding
   is capped at 4096×4096 and 256 MB. Spotify's largest covers are 640 px. (No crash could be shown before: the
   decoder fails on a lying header before allocating; this is a tighter fence, not a fixed bug.) Still to do: a body
   without a length is buffered before the check; a streaming cap would close that.
6. **crash (hardening)** — the Core Audio tap callback (macOS, the app as Engine) called Rust with nothing to catch a
   panic, which would unwind into Core Audio's thread; now the buffer is dropped instead.
7. **data/annoyance** (found during #62) — a volume set while Soloist restarted was lost, and a volume of exactly 0 was
   never saved (`1ce954b`).

### Checked, fine

- **Secrets**: the Keychain and Secret Service get values over stdin (`security -i` with hex, `secret-tool store`),
  never on a command line. Exception, documented since #2: Soloist only takes its key as `--api-key`, so on Linux it
  shows in `ps` to local users (in the macOS VM, only inside the guest). Inherent to Soloist.
- **Subprocesses**: every `Command::new` uses fixed arguments or passes values as separate argv entries; notification
  text reaches `osascript` as `argv`, not spliced into the script; `pkill -x Spotify`/`spotify` match exact names.
  `secret-tool`, `pactl`, `parec`, `pgrep`, `pkill`, `tar` are found on `PATH` (polish: absolute paths).
- **Terminal output**: all text goes through ratatui's `set_stringn`, which drops control characters, so an escape
  sequence in a track or playlist name can't reach the terminal; the only raw writes are kitty graphics commands built
  from numbers and an OSC 52 copy that is base64.
- **Panics outside tests** in the Daemon and config: the rest are invariants (static regexes, the default config
  parsing, `Mutex` poisoning after another panic, `unreachable!` behind a match on the same value).
- **Protocol, a Client that stops reading**: memory always stayed bounded (events reach each Client through a
  broadcast channel that skips ahead for a slow one), but such a Client was never let go: its tasks stayed blocked for
  as long as it was connected. **Fixed**: everything to a Client, the initial snapshot included, goes through one
  writer with a 5 s deadline per message; a Client that takes nothing for 5 s has its session closed (a real Client
  reconnects by itself). Test: `a_client_that_stops_reading_is_let_go` (fails without the fix).
- **`follow_config`** stats `config.toml` once a second: one tiny syscall a second; acceptable (file watching would
  add a dependency for nothing measurable).
- **macOS socket path** `…/T/singularity-user/…`: `uid()` reads `/proc`, which macOS lacks, so the fallback name says
  "user". Harmless (macOS's `$TMPDIR` is already private to the user); renaming it would strand a running Daemon on the
  old path. Polish.

- **`unsafe`** (Client: kitty shared memory, `proc_name`, `kill`, `getrusage`, libproc; Daemon: libproc, Core Audio,
  Now Playing's run loop, `localtime_r`, `prctl` in `pre_exec`, `fchmod`): buffers sized before every call, counts
  bounds-checked, the shared-memory segment created exclusively (`O_EXCL`, 0600) and unlinked on every failure path
  and after 2 s, `kill` only after checking the pid is a `singularityd`. Fine apart from finding 6. Miri can't run
  FFI, so these stay reviewed by hand.
- **Migrations**: the listening log from `user_version` 1 → 2 and config schemas 1 → 3 have tests that keep every row
  and every comment; DST and midnight have `tests/stats_tz.rs`.

- **String slicing** in parsers (`&s[a..b]`): every position comes from `find` on the same string or is a fixed
  ASCII text, so no slice can split a character.
- **Timers and polling loops** in the Daemon: each wakes at most 4× a second while idle (the tap waiting for music
  1×/s, the app-tap manager 1×/s, the VM's PCM accept loop 4×/s, `follow_config` 1×/s, librespot's watchdog every
  5 s); the idle Daemon measures ~0 % CPU.

### Resources, measured (macOS, release, idle, nothing playing)

The owner's own idle Client: **9–10 % CPU**, 80 MB RSS; its Daemon (librespot) ~0 %, 6 MB. `sample` shows the Client's
main thread mostly waiting; the work is drawing and sending the animated Visuals' frames to the terminal
(`Kitty::transmit`): they animate while nothing plays. In the pty harness (fake Daemon, default layout):

| Client | focused (30 fps) | unfocused (10 fps) |
|--------|------------------|--------------------|
| pixel tier (kitty images) | 5.5 % | 2.3 % |
| cell tier | 2.8 % | 1.2 % |

The terminal's own work decoding those frames comes on top.

**Fixed (D60, owner: "slow sounds good")**: while nothing plays and nothing was touched for 2 s, the Client draws at
most 5 frames a second. Same harness, focused: pixel tier **5.5 → 2.1 %**, cell tier **2.8 → 1.2 %**. What's left is
the cost of one frame (~4 ms in the pixel tier: the whole screen plus the hole's image); worth a look in the frame
profile still to do (a frame that changed nothing could skip the image upload).
